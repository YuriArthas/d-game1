# 单机塔防游戏 Draft

状态：Draft

本文是当前 Three.js 单机塔防方向的设计基线。它只描述已经确认的范围、对象边界、数据和阶段，不代表所有内容已经实现。

## 1. 目标

制作一个在浏览器中运行的单机 3D 塔防游戏：玩家在俯视地图上放置防御塔，阻止怪物沿路线到达终点。

游戏逻辑不依赖后端、账号、多人房间、匹配服务或外部 CDN。现有测试入口与文件服务继续沿用。

当前仓库外层保留一个测试服务器和游戏列表，构建入口为 `dist/index.html`。2026-10-01 用户明确不做独立游戏入口和静态交付，不再拆分交付包；现有构建与运行方式保留。

## 2. 已确认规格

| 项目 | 当前决定 |
| --- | --- |
| 游戏模式 | 纯单机 |
| 渲染 | Three.js WebGL2 |
| UI 与场景组织 | React + React Three Fiber |
| 源码 | TypeScript，面向对象 |
| 关卡数量 | 约 50 关 |
| 怪物 | 约 20 种玩法类型 |
| 同屏规模 | 约 50 个活动怪物 |
| 防御塔 | 约 10 种 |
| 升级 | 每种塔 1～5 级 |
| 升变 | 5 级后获得额外特性；第一版每种塔先做一个固定升变结果 |
| 镜头 | 固定的正交或弱透视 3/4 俯视角 |
| 建造 | 网格放置；第一版每座塔占一格，路线不可建造，不做堵路和动态寻路 |
| 物理 | 正式游戏暂不使用物理引擎 |
| 怪物表现 | 至少具备 idle、walk、death 动作 |
| 运行环境 | 桌面浏览器和移动浏览器 |
| 网络 | 无网络游戏逻辑；静态 HTTP 只负责提供文件 |

“20 种怪物”暂时指 20 种玩法定义。是否要求 20 个完全不同的模型，作为内容成本决策单独确认。

## 3. 核心玩法

一局游戏由关卡、波次、路线和防御塔组成：

```text
选择关卡
  -> 读取地图、路线、波次和可用防御塔
  -> 玩家放置防御塔
  -> 开始波次
  -> 怪物沿路线移动
  -> 防御塔查找目标并攻击
  -> 怪物死亡或抵达终点
  -> 波次奖励与下一波
  -> 全部波次完成则胜利，基地生命归零则失败
```

第一版不做多人，也不把其他玩家伪装成 NPC。屏幕上的所有怪物都是本地游戏对象。

## 4. 运行时对象边界

### GameNode

`GameNode` 只负责对象生命周期和拓扑：

- 创建、启动、停止和销毁；
- 父子节点关系；
- 子节点释放顺序；
- 资源和监听器清理。

它不负责 AI、攻击、升级、动画选择或胜负规则。

### GameWorld

`GameWorld` 在这里表示一局游戏的根职责；当前玩法实现命名为 `BattleWorld`，与旧 `runtime-test/GameWorld` 探针区分。它负责：

- 当前关卡运行上下文；
- 波次推进；
- 玩家资源和基地生命；
- 敌人与塔的登记 Map，以及地图运行时引用；
- 游戏暂停、胜利、失败和重新开始。

`GameWorld` 不直接实现每一种怪物或防御塔的具体行为。

### Unit

`Unit` 是一个游戏单位的稳定身份边界，不是通用数据包装器，也不是无类型的 `Component[]` 容器。

```text
Unit
  id
  definitionId
  state
  view
  animation
  owned behavior objects
```

按实际复杂度拆分单位拥有的行为对象；下列是职责分配，不是需要提前建立的 Controller 类清单：

```text
EnemyUnit
  当前生命、路线进度、位置和朝向
  移动、受伤与逻辑死亡
  自己的 View 和动画播放状态

TowerUnit
  建造格、当前目标、冷却和等级
  索敌、攻击与升级执行
  自己的 View
```

单位自己的能力对象拥有查询、调度、路线、攻击和死亡执行生命周期。全局对象只提供时间、地图索引和只读查询入口，不把所有单位逻辑集中到一个巨型 `GameSystem` 中。

当前探针直接由 `GameWorld` 和 `EnemyUnit` 持有状态、调用清理方法；尚未建立 `GameNode` 通用基类，也不为几个字段提前拆出独立状态包装器。共享的 `RoutePath` 只保存路线几何与采样方法，单位自己保存进度，不把几何采样器误命名为独立运行的路线行为。

实际玩法现在由一个 `BattleWorld` 持有建造、波次、金币、生命和结算；原 `PlacementWorld` 已移除。格子到 `TowerUnit` 的 Map 同时作为塔登记表与占用索引。`TowerUnit` 自己索敌、锁定目标并推进攻击时间；`ProjectileUnit` 保存原目标并执行追踪和命中判断；`EnemyUnit` 保存生命、移动进度并执行死亡。World 只按命中结果结算一次伤害、奖励与登记清理。原 `runtime-test/GameWorld` 保留为独立探针，复用实际玩法的 `RoutePath`、`EnemyUnit` 和骷髅 View，不再拥有另一份怪物行为实现。

### View 与 Animation

游戏状态和 Three.js 表现分开：

- `EnemyUnit` 直接保存生命、路线进度和状态，内容定义保存奖励；
- View 持有 Three.js `Object3D`；
- 当前 View 同时持有 `AnimationMixer` 和动作句柄，没有为单个模型另建 Controller；
- 状态转换驱动动作播放；
- 动画播放完成不能反向决定怪物是否死亡。

怪物进入死亡状态后，游戏逻辑先处理奖励、移除目标资格和生命周期；表现层再播放 death 动作，随后释放视图。

波次完成由“待生成为零且活动敌人为零”决定。死亡视图仍可保留，不能延迟波次奖励或下一波；逻辑完成也不能自动暂停死亡表现。暂停是单独的玩家操作，冻结逻辑与表现；恢复后继续清理。探针的波次时间在逻辑完成时停止，实例释放计数可以随后继续变化。

## 5. 怪物设计

20 种怪物使用数据定义加少量行为策略，不为每一个数值变体创建一个类。

建议的行为类别包括：

- 普通地面移动；
- 高速移动；
- 高生命或护甲；
- 飞行或特殊路线；
- 死亡分裂；
- 护盾或减伤；
- 治疗或辅助；
- Boss。

P3 正式怪物所需的数据语义如下；当前 P2 最小字段以第 7 节为准，资源与行为引用在接入实际功能时再加入：

```text
id
modelKey
animationSetKey
maxHealth
moveSpeed
armor / resistance
reward
baseDamage
behaviorKey
```

怪物沿 `RouteData` 的 waypoint 移动，不使用刚体。路线进度、位置和切线朝向由单位逻辑计算，View 只同步结果；出生和折点朝向不依赖前一帧模型位置。

## 6. 防御塔设计

10 种防御塔共享 `TowerUnit` 基础对象，通过数据和攻击策略产生差异。

攻击策略初步包括：

- 单目标攻击；
- 范围攻击；
- 穿透攻击；
- 减速攻击；
- 持续伤害；
- 辅助或增益。

P3 塔数据最终需要覆盖以下语义；当前只落地了建造和单箭攻击所需部分，等级、升级与升变尚未落地；升级与升变先内嵌在每种塔的定义中，出现实际复用需求后再拆独立表：

```text
id
modelKey
cost
targetPolicy
attackStrategy
range
damage
attackInterval
levels
ascension
```

升级数据不写入 `TowerUnit` 的分支代码：

```text
Tower Level 1
  -> Level 2
  -> Level 3
  -> Level 4
  -> Level 5
  -> Ascension
```

第一版每种塔只有一个固定升变结果。升变可以增加攻击范围、目标数量、攻击类型、状态效果或新的视觉表现。

上述是后续玩法语义，不一次性变成必填字段。当前箭塔仅有 ID、费用，以及已被战斗消费的射程、伤害、攻击间隔、出箭延迟和箭矢速度。首个箭塔直接实现一种索敌和攻击规则；等级、升级表、攻击类型、策略 ID 与资源注册表尚未加入，出现实际第二种行为后再考虑策略拆分。

## 7. 关卡与数据

50 关使用内容数据定义，不写 50 个关卡类。数据定义和运行时状态分开：内容只保存可序列化值和 ID 引用；`GameWorld`、`EnemyUnit` 和 `TowerUnit` 保存当前生命、路线进度、等级、冷却等动态事实。

第一阶段先使用三个文件，避免在样本很少时拆出过多模块：

```text
src/games/tower-defense/data/
  types.ts      # 最小数据类型
  content.ts    # 样例内容
  catalog.ts    # ID 和引用校验
```

正式数据的坐标使用数字 tuple，不把 `Vector3`、`Mesh` 或 `AnimationMixer` 放进数据层：

```ts
type Vec3Data = readonly [number, number, number];
type Vec2Data = readonly [number, number];
type GridCell = readonly [column: number, row: number];

interface BuildGridData {
  origin: Vec2Data; // X/Z 平面上 (0,0) 格的角点
  cellSize: number;
  buildableCells: readonly GridCell[];
}

interface TowerData {
  id: string;
  cost: number;
  range: number;           // X/Z 平面射程
  damage: number;          // 每次实际命中的伤害
  cooldown: number;        // 两次攻击开始的最小间隔，秒
  windup: number;          // 锁定后到逻辑出箭点，秒
  projectileSpeed: number; // 箭尖追踪速度，米/秒
}

interface RouteData {
  id: string;
  waypoints: readonly Vec3Data[];
}

interface EnemyData {
  id: string;
  maxHealth: number;
  moveSpeed: number;
  reward: number;
}

interface SpawnEntry {
  enemyId: string;
  count: number;
  interval: number;
  routeId: string;
}

interface WaveData {
  id: string;
  entries: readonly SpawnEntry[];
  reward: number;
}

interface MapData {
  id: string;
  routeIds: readonly string[];
  buildGrid?: BuildGridData;
}

interface LevelData {
  id: string;
  mapId: string;
  waveIds: readonly string[];
  startingGold: number;
  baseLives: number;
}
```

当前落地 `RouteData`、`EnemyData`、`SpawnEntry`、`WaveData`、`MapData`、`LevelData`、`TowerData` 和地图内嵌的 `BuildGridData`。塔有 ID、费用及上面列出的五个已消费攻击参数；网格仅有原点、边长和可建造格。原有路线专用探针没有建造区，所以 `buildGrid` 可缺省；进入建造世界时必须存在，缺失直接报错，不生成默认网格。

升级、攻击策略、抗性和关卡 modifiers 以对应玩法存在为前提。暂不建立独立升级表，不为未来字段预留无约束对象。格子占用、金币、选中位置和塔实例不写回内容定义。

定义由 TypeScript 只读约束，运行期间不修改内容；不支持热更。`ContentCatalog` 在加载时检查 ID 唯一性、关卡到地图和波次的引用、波次到敌人和路线的引用，以及波次路线是否属于关卡地图。引用缺失直接报错，不使用静默默认值。运行时对象只通过 ID 读取定义，不复制另一份内容配置。

内容合法性在加载边界检查一次，运行时内部按已成立的类型和生命周期契约执行。不要逐帧重复校验、吞掉错误后跳过单位、自动修补配置或为未实现功能建立兜底分支。生成、暂停、死亡、完成和释放的状态判断属于真实业务规则；异步加载取消和重复 dispose 的清理语义保留。

P2 验证页明确选择一个关卡中的一个波次：全部生成项并行执行，各项首个单位在 t=0 生成，后续每隔 `interval` 秒生成；`interval=0` 表示同一时刻全部生成。不会忽略剩余生成项或用显示颜色数量限制单位数。多波关卡在测试页逐波选择，自动推进与经济/胜负规则留到 P3。

逻辑以 1/60 秒固定步推进，后台恢复单帧最多追赶 0.25 秒；每个渲染帧只按该单位实际累计的模拟时间推进一次表现。新生单位不补出生之前的动画，逻辑死亡时丢弃本帧尚未展示的行走时间，死亡动作只累计死亡后的时间；动作切换可以零步同步初始姿态。暂停冻结生成、移动、攻击、飞行箭矢和死亡表现。

逻辑死亡立即失去活动资格，球体完成 0.8 秒缩小后释放，骷髅完成 Death_A 单次动作后释放。骷髅先作为测试页 View 工厂接入，共享模板，角色之间使用独立骨骼和 Mixer；同一角色内保留源 GLB 的共享 skin 关系，不把多个网格的同一套骨骼重复计算。不为这个探针扩充通用模型注册框架。已释放单位从保留容器移除，只保留统计数，重开清理旧单位和待生成项。

关卡参数和已实现的单位数值必须有单一读取位置。修改源数据并重新构建后，运行时必须读取修改后的值。地图第一版可以使用少量地图模板，通过路线、入口、出口、可放置区域、波次和规则组合出 50 关；若确定需要 50 张独立地图，模型和关卡制作成本需要重新评估。

## 8. 模型与动作资源

运行时使用本地 GLB 资源和 Three.js `GLTFLoader`。当前探针由模板对象直接管理资源；接入多种正式资源时再建立明确的资源引用与目录，不提前要求 `modelKey`、`animationSetKey` 和通用 registry。

每个可用怪物模型至少需要：

- 稳定的根节点和比例；
- idle 动作；
- walk 动作；
- death 动作；
- 清晰的动作 clip 名称或映射；
- 可用于最终交付的来源和许可证。

缺少明确要求的动作时，资源校验应报告缺失，不把 idle 静默替代为 walk 或 death。

先验证一套模型和动作资源能完整经过：

```text
GLB 加载
  -> clip 解析
  -> semantic action 映射
  -> AnimationMixer 播放
  -> death 后视图释放
```

完成这条链路后再批量扩展 20 种怪物。最终资源清单必须记录模型、动画、贴图、音效和字体的来源、许可证和限制。

## 9. 镜头与输入

使用固定 3/4 俯视角。地图放置通过射线投射到地面，再换算到网格：

- 桌面端：鼠标点击、拖拽、滚轮缩放；
- 移动端：触摸点击、拖动平移、双指或按钮缩放；
- 放置前显示合法格、射程（接入攻击后）、费用和占用；
- 放置确认由游戏逻辑决定，UI 只提交玩家意图。

第一版不做自由飞行相机、不做复杂编辑器、不做物理拖拽。

当前已实现点击/触摸选格、模型与射程圈预览、确认与取消；镜头平移缩放另行接入。两端共用同一套建造判定，UI 按钮不穿透到地图。地图只定义网格原点（0,0 格的角点）、格子边长和可建造格坐标列表；放置位置为格子中心。可建造列表在内容制作时排除路线区域，不生成第二份运行时阻挡配置。取格使用 `floor((坐标 - 原点) / 边长)`，不把地图外点击裁剪回有效格。

首个塔占一格，暂不增加 footprint 字段。格子占用、金币和已建塔属于运行时。确认时由 World 检查合法格、占用和费用，View 创建成功后才一起提交扣款和登记。业务拒绝保持原状态并显示具体原因；资源/程序错误直接上抛，不产生费用或占用。预览结果不代替确认时的业务判断。

建造页初始可操作；暂停保留当前预览、禁止改选和确认建造，允许取消预览、恢复及重开。重开恢复初始金币、清空塔和选中位置，并回到可操作状态。拖动超过点击阈值、取消的触摸和双指操作不当作选格；点击已有塔仍选择它实际占用的格子。CPU/GPU 摘要位于工具栏，避免遮住可建格。

## 10. React 与游戏循环

React 负责：

- 菜单；
- 塔选择栏；
- 金币、生命和波次显示；
- 升级面板；
- 暂停、胜利和失败界面。

React 不负责每帧保存 50 个怪物的位置，也不使用每帧 `setState` 驱动游戏。

游戏循环负责：

```text
每个渲染帧
  -> 累积时间，执行零到多个固定逻辑步
     -> 波次生成
     -> 单位移动、索敌、攻击与命中
     -> 死亡/漏怪、经济与波次/胜负结算
  -> 每个保留 View 同步最终位置与朝向
  -> 按各单位累计的模拟时间推进一次动画
  -> 释放已结束的死亡 View
  -> SceneRenderer 提交一次 Three.js 渲染
```

路线探针保留生成、移动、死亡与释放实验；建造页现在由 `BattleWorld` 串起建造、攻击、命中、奖励、漏怪扣命与三波胜负。`SceneRenderer` 是明确的单次渲染入口，帧计时是可关闭的探针；关闭计时不影响渲染。HUD 标为“帧循环 CPU”，范围不含 React/DOM、其他页面脚本或浏览器合成。GPU 异步取样，不与当前 CPU 值相加；运行时页保留完整帧号和提交信息，建造页显示紧凑 CPU/GPU 摘要。

帧耗时与旧运行时探针摘要每 250ms 刷新；战斗状态每 100ms 刷新。摘要不遍历单位，逐单位和骨骼详情只在展开时采集，关闭后不再序列化。状态组件的轮询不重新渲染 Canvas 子树；建造、重开、金币/生命/阶段变化会更新相关 UI 与格子显示。

## 11. 当前明确不做

- 多人和网络同步；
- 后端服务；
- 独立游戏入口和静态交付包；
- Rapier 或其他物理引擎；
- 50 个独立地图的完整美术生产；
- 每种塔多分支升变；
- 通用 ECS 框架；
- 通用游戏编辑器；
- 自定义 WebGPU 渲染器；
- 复杂技能树、装备和账号系统。

## 12. 大 Phase 与难度

#### P1.1 的选型范围

- 优先调查模型自带移动和死亡动作的资源包；若模型与动作分开采购或下载，显式核验骨骼兼容性，不能仅凭骨骼名称相同认为可直接共用。
- 授权核验包含商业游戏使用、修改、静态站点分发以及向甲方交付源素材的条件。允许商用不自动等于允许交付原始素材。
- 本步输出候选与推荐样本，不批量购买或生产 20 种怪物。收费样本或额外授权要求单独列出。
- 若所有候选都缺少必要动作，记录缺口与制作/重定向成本，再决定样本；不以静止模型替代动作验证。

#### P1.2 的图片边界

- 后台渲染 PNG 与 Blender 编辑器窗口截图分别验证、分别标记。
- 后台渲染可使用 CPU，不要求当前机器有可用 GPU。
- 编辑器截图需要图形会话或虚拟显示；后台渲染成功不能记为编辑器截图成功。编辑器截图不可用时明确报告，再讨论是否需要补齐该环境。
- 本步只验证工具；样本的移动/死亡动画正确性由 P1.3～P1.5 证明。

#### P1.3～P1.6 的实现边界

- 样本使用 glTF 支持的材质；Blender 中专有的材质节点需转换或烘焙，不能预设导出前后效果相同。
- 保留动作名称、时长、循环方式与语义映射。若源动作带根位移，明确处理后再导出，避免与路线移动叠加。
- 播放控制只需最小测试按钮或脚本；暂不开发波次、攻击、伤害、升级或关卡系统。
- 模型实例、骨骼和播放状态必须独立；资源模板可共享。销毁单个实例不得释放仍被其他实例使用的材质、纹理和几何体。
- P1.6 只验证实例隔离和基本释放；约 50 个怪物、长时间内存趋势及真实手机性能放在 P2。

P1 的执行顺序为 **P1.1 → P1.2 → P1.3 → P1.4 → P1.5 → P1.6**。P1.3 依赖已选样本和 Blender 工具可用；后续每步复用同一份已验证样本。

P1 收尾需展示：样本来源与授权记录、源文件与 GLB、导出命令、Blender 图片、浏览器模型截图、动作播放证据、多实例验证结果和尚存缺口。先据此讨论是否进入 P2，不自动扩大到批量资产制作。

当前攻击时序补充：每个 1/60 秒逻辑步先生成和移动敌人、处理到达出口，再推进已有箭矢并结算命中，最后推进塔的锁定/出箭。新箭在下一逻辑步开始飞行；同一步到达出口的目标优先按漏怪处理。单帧最多补 0.25 秒；所有怪物动作、塔姿态和箭矢位置在逻辑推进后每渲染帧统一呈现。塔动作按逻辑攻击年龄映射到 Shoot 的 0.5 秒出箭点；加载时缓存该姿态的箭尖位置，逻辑不读取上一渲染帧的骨骼矩阵。取消出箭仍完成该次动作与冷却。

## 13. 推进规则与验证边界

阶段概览为 P1 → P2 → P3 → P4 → P5。用户已确认三波版本可玩并要求开始正式游戏设计，当前进入 P3 的设计讨论；P1/P2 尚存的资源与实机验证单独追踪，不据此标为已完成。
