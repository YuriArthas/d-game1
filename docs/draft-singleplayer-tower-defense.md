# 单机塔防游戏 Draft

状态：Draft

本文是当前 Three.js 单机塔防方向的设计基线。它只描述已经确认的范围、对象边界、数据和阶段，不代表所有内容已经实现。

## 1. 目标

制作一个可以在浏览器中独立运行的单机 3D 塔防游戏：玩家在俯视地图上放置防御塔，阻止怪物沿路线到达终点。

游戏不依赖后端、账号、多人房间、匹配服务或外部 CDN。构建产物通过普通静态 HTTP 服务即可启动和完成基本游玩。

当前仓库外层保留一个测试服务器和游戏列表。测试服务器只用于本地和公网测试，不属于最终游戏运行代码。游戏自身的构建入口仍然是 `dist/index.html`。

## 2. 已确认规格

| 项目 | 当前决定 |
| --- | --- |
| 游戏模式 | 纯单机 |
| 渲染 | Three.js WebGL2 |
| UI 与场景组织 | React + React Three Fiber |
| 源码 | TypeScript，面向对象 |
| 关卡数量 | 约 50 关 |
| 怪物 | 约 20 种玩法类型 |
| 同屏规模 | 约 50 个活动怪物 |
| 防御塔 | 约 10 种 |
| 升级 | 每种塔 1～5 级 |
| 升变 | 5 级后获得额外特性；第一版每种塔先做一个固定升变结果 |
| 镜头 | 固定的正交或弱透视 3/4 俯视角 |
| 物理 | 正式游戏暂不使用物理引擎 |
| 怪物表现 | 至少具备 idle、walk、death 动作 |
| 运行环境 | 桌面浏览器和移动浏览器 |
| 网络 | 无网络游戏逻辑；静态 HTTP 只负责提供文件 |

“20 种怪物”暂时指 20 种玩法定义。是否要求 20 个完全不同的模型，作为内容成本决策单独确认。

## 3. 核心玩法

一局游戏由关卡、波次、路线和防御塔组成：

```text
选择关卡
  -> 读取地图、路线、波次和可用防御塔
  -> 玩家放置防御塔
  -> 开始波次
  -> 怪物沿路线移动
  -> 防御塔查找目标并攻击
  -> 怪物死亡或抵达终点
  -> 波次奖励与下一波
  -> 全部波次完成则胜利，基地生命归零则失败
```

第一版不做多人，也不把其他玩家伪装成 NPC。屏幕上的所有怪物都是本地游戏对象。

## 4. 运行时对象边界

### GameNode

`GameNode` 只负责对象生命周期和拓扑：

- 创建、启动、停止和销毁；
- 父子节点关系；
- 子节点释放顺序；
- 资源和监听器清理。

它不负责 AI、攻击、升级、动画选择或胜负规则。

### GameWorld

`GameWorld` 是一局游戏的根对象，负责：

- 当前关卡运行上下文；
- 波次推进；
- 玩家资源和基地生命；
- `EnemyRegistry`、`TowerRegistry` 和地图运行时引用；
- 游戏暂停、胜利、失败和重新开始。

`GameWorld` 不直接实现每一种怪物或防御塔的具体行为。

### Unit

`Unit` 是一个游戏单位的稳定身份边界，不是通用数据包装器，也不是无类型的 `Component[]` 容器。

```text
Unit
  id
  definitionId
  state
  view
  animation
  owned behavior objects
```

具体单位使用组合能力：

```text
EnemyUnit
  HealthController
  RouteFollower
  EnemyBehavior
  DeathController
  UnitAnimationController
  EnemyView

TowerUnit
  TargetingController
  AttackController
  UpgradeController
  TowerView
```

单位自己的能力对象拥有查询、调度、路线、攻击和死亡执行生命周期。全局对象只提供时间、地图索引和只读查询入口，不把所有单位逻辑集中到一个巨型 `GameSystem` 中。

### View 与 Animation

游戏状态和 Three.js 表现分开：

- `EnemyState` 保存生命、路线进度、状态和奖励等游戏事实；
- `EnemyView` 持有 Three.js `Object3D`；
- `UnitAnimationController` 持有 `AnimationMixer` 和当前动作句柄；
- 状态转换驱动动作播放；
- 动画播放完成不能反向决定怪物是否死亡。

怪物进入死亡状态后，游戏逻辑先处理奖励、移除目标资格和生命周期；表现层再播放 death 动作，随后释放视图。

## 5. 怪物设计

20 种怪物使用数据定义加少量行为策略，不为每一个数值变体创建一个类。

建议的行为类别包括：

- 普通地面移动；
- 高速移动；
- 高生命或护甲；
- 飞行或特殊路线；
- 死亡分裂；
- 护盾或减伤；
- 治疗或辅助；
- Boss。

每个怪物定义至少包含：

```text
id
modelKey
animationSetKey
maxHealth
moveSpeed
armor / resistance
reward
baseDamage
behaviorKey
```

怪物沿 `RouteDefinition` 的 waypoint 或 segment 移动，不使用刚体。路线进度是游戏事实，渲染层根据进度计算世界位置。

## 6. 防御塔设计

10 种防御塔共享 `TowerUnit` 基础对象，通过数据和攻击策略产生差异。

攻击策略初步包括：

- 单目标攻击；
- 范围攻击；
- 穿透攻击；
- 减速攻击；
- 持续伤害；
- 辅助或增益。

塔定义至少包含：

```text
id
modelKey
cost
targetPolicy
attackStrategy
range
damage
attackInterval
upgradeIds
ascensionId
```

升级数据不写入 `TowerUnit` 的分支代码：

```text
Tower Level 1
  -> Level 2
  -> Level 3
  -> Level 4
  -> Level 5
  -> Ascension
```

第一版每种塔只有一个固定升变结果。升变可以增加攻击范围、目标数量、攻击类型、状态效果或新的视觉表现。

## 7. 关卡与数据

50 关使用内容数据定义，不写 50 个关卡类。

```text
data/
  enemies/
  towers/
  upgrades/
  maps/
  routes/
  waves/
  levels/
  animations/
```

核心数据结构：

```text
LevelDefinition
  mapId
  routeIds
  waveSetId
  startingGold
  baseLives
  allowedTowerIds
  modifiers

WaveDefinition
  entries: enemyId + count + interval + routeId
  reward

AnimationSetDefinition
  idle
  walk
  death
  attack?
```

关卡参数、怪物数值、塔数值、升级效果和规则必须有单一读取位置。修改源数据并重新构建后，运行时必须读取修改后的值。

地图第一版可以使用少量地图模板，通过路线、入口、出口、可放置区域、波次和规则组合出 50 关。若确定需要 50 张独立地图，模型和关卡制作成本需要重新评估。

## 8. 模型与动作资源

运行时使用本地 GLB 资源和 Three.js `GLTFLoader`。模型和动画资源由 registry 管理，单位只引用 `modelKey` 和 `animationSetKey`。

每个可用怪物模型至少需要：

- 稳定的根节点和比例；
- idle 动作；
- walk 动作；
- death 动作；
- 清晰的动作 clip 名称或映射；
- 可用于最终交付的来源和许可证。

缺少明确要求的动作时，资源校验应报告缺失，不把 idle 静默替代为 walk 或 death。

先验证一套模型和动作资源能完整经过：

```text
GLB 加载
  -> clip 解析
  -> semantic action 映射
  -> AnimationMixer 播放
  -> death 后视图释放
```

完成这条链路后再批量扩展 20 种怪物。最终资源清单必须记录模型、动画、贴图、音效和字体的来源、许可证和限制。

## 9. 镜头与输入

使用固定 3/4 俯视角。地图放置通过射线投射到地图平面或放置网格：

- 桌面端：鼠标点击、拖拽、滚轮缩放；
- 移动端：触摸点击、拖动平移、双指或按钮缩放；
- 放置前显示合法区域、费用和碰撞占用；
- 放置确认由游戏逻辑决定，UI 只提交玩家意图。

第一版不做自由飞行相机、不做复杂编辑器、不做物理拖拽。

## 10. React 与游戏循环

React 负责：

- 菜单；
- 塔选择栏；
- 金币、生命和波次显示；
- 升级面板；
- 暂停、胜利和失败界面。

React 不负责每帧保存 50 个怪物的位置，也不使用每帧 `setState` 驱动游戏。

游戏循环负责：

```text
固定时间步
  -> GameWorld.tick
  -> WaveDirector
  -> EnemyUnit 行为
  -> TowerUnit 行为
  -> AnimationMixer 更新
  -> View 同步
  -> Three.js 渲染
```

## 11. 当前明确不做

- 多人和网络同步；
- 后端服务；
- Rapier 或其他物理引擎；
- 50 个独立地图的完整美术生产；
- 每种塔多分支升变；
- 通用 ECS 框架；
- 通用游戏编辑器；
- 自定义 WebGPU 渲染器；
- 复杂技能树、装备和账号系统。

#### P1.1 的选型范围

- 优先调查模型自带移动和死亡动作的资源包；若模型与动作分开采购或下载，显式核验骨骼兼容性，不能仅凭骨骼名称相同认为可直接共用。
- 授权核验包含商业游戏使用、修改、静态站点分发以及向甲方交付源素材的条件。允许商用不自动等于允许交付原始素材。
- 本步输出候选与推荐样本，不批量购买或生产 20 种怪物。收费样本或额外授权要求单独列出。
- 若所有候选都缺少必要动作，记录缺口与制作/重定向成本，再决定样本；不以静止模型替代动作验证。

#### P1.2 的图片边界

- 后台渲染 PNG 与 Blender 编辑器窗口截图分别验证、分别标记。
- 后台渲染可使用 CPU，不要求当前机器有可用 GPU。
- 编辑器截图需要图形会话或虚拟显示；后台渲染成功不能记为编辑器截图成功。编辑器截图不可用时明确报告，再讨论是否需要补齐该环境。
- 本步只验证工具；样本的移动/死亡动画正确性由 P1.3～P1.5 证明。

#### P1.3～P1.6 的实现边界

- 样本使用 glTF 支持的材质；Blender 中专有的材质节点需转换或烘焙，不能预设导出前后效果相同。
- 保留动作名称、时长、循环方式与语义映射。若源动作带根位移，明确处理后再导出，避免与路线移动叠加。
- 播放控制只需最小测试按钮或脚本；暂不开发波次、攻击、伤害、升级或关卡系统。
- 模型实例、骨骼和播放状态必须独立；资源模板可共享。销毁单个实例不得释放仍被其他实例使用的材质、纹理和几何体。
- P1.6 只验证实例隔离和基本释放；约 50 个怪物、长时间内存趋势及真实手机性能放在 P2。

P1 的执行顺序为 **P1.1 → P1.2 → P1.3 → P1.4 → P1.5 → P1.6**。P1.3 依赖已选样本和 Blender 工具可用；后续每步复用同一份已验证样本。

P1 收尾需展示：样本来源与授权记录、源文件与 GLB、导出命令、Blender 图片、浏览器模型截图、动作播放证据、多实例验证结果和尚存缺口。先据此讨论是否进入 P2，不自动扩大到批量资产制作。

P2.2 的数量口径需要记录：活动怪物、死亡动画实例、防御塔和投射物分别计数。当前约 50 个活动怪物不能被误写成整个画面总共只有 50 个对象。

## 13. 推进规则与验证边界

顺序为 P1 → P2 → P3 → P4 → P5。已有平面方块脚手架只是基础证据，不能把 P1/P2 标为已完成。

- 技术验证只实现验证该问题所需的小样本，不提前开发整套游戏或批量内容。
- P1/P2 完成后再收敛正式对象结构和资产规范；原型代码是否保留根据结果决定。
- P3 通过后，P4 按内容批次推进，不一次性生成 50 关再集中试玩。
- 移动端、动画、资源释放和独立交付在 P2 就验证，P5 再做整体验收。
- 无头 Chromium + SwiftShader 可以提供画面检查证据，不作为真实手机 GPU 性能证据；缩小浏览器视口也不等于移动设备验收。
- Blender 渲染图可验证模型、姿态、材质；Three.js 浏览器画面才验证最终运行效果。两者不能互相代替。
- 每次交付说明本步已验证内容和未验证内容，不因单步通过而自动进入下一大 Phase。

## 14. 当前需要继续确认的决策

1. 50 关是否复用少量地图模板，还是要求 50 张独立地图。
2. 20 种怪物是 20 种玩法定义，还是 20 个完全不同的视觉模型。
3. 塔的升变是否每种一个固定结果，还是要做多分支。
4. 防御塔放置使用固定点、网格，还是自由位置。
5. 是否需要塔的攻击动作，还是第一版只要求怪物的移动和死亡动作。

在这些问题确认前，不应开始批量制作 50 关或 20 套模型。
